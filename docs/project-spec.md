# Synthetic EHR + "Privacy-by-Design": project spec

> The source of truth. Written before any code. When building shows a part to be wrong, change it here and record why under [Changes to the spec](#changes-to-the-spec).

Status: **draft, 2026-11-15; all decisions (D1–D5) made 2026-11-26.** The decisions in [Open decisions](#open-decisions) are the owner's to make; each has a recommendation. Until they are made, the parts that depend on them are marked *(depends on D1)* and so on.

A realistic but entirely fake electronic health record (EHR): patients, visits, diagnoses, medications and lab results, generated in Python with `Faker` and explicit clinical rules. On top of it: a normalized source schema, analytical marts, a small app for cohorts, visit timelines and drug–lab interactions, and a governance pack that treats the fake data as if it were real.

## What this proves

The CV line: "Built a synthetic EHR generator with clinically plausible rules, a normalized and an analytical schema, and a cohort-exploration app, designed privacy-by-design: pseudonymization, role-based access, small-cell suppression, a data dictionary and a DPIA-style assessment, each with a test that runs in CI; and a hyperkalaemia prediction model, compared with a rule baseline and checked against the effects planted in the data."

## Data

- **Source and licence:** none. Every row is generated by this project's code from a seed. No real person's data is used at any stage, and the generator never reads real records, so no real person can be re-identified from it.
- **Codes used inside the data:** ICD-10 for diagnoses, ATC for medicines, LOINC for lab tests, a few dozen codes each. Their terms of use must be checked and written in the README before they are committed (checklist step 2).
  - **ICD-10** (checked 2026-11-26): codes from the WHO's ICD-10, 2019 edition. The WHO's [licensing page for its classifications](https://www.who.int/about/licensing/classifications/en/) lists ICD under CC BY-ND 3.0 IGO (use allowed with citation and without changing the codes), but no WHO page states ICD-10's own licence outright. So only the bare codes (e.g. `E11`) are committed for now, with the WHO cited; the WHO's titles are added only after the owner has the WHO's written answer (asked via icd@who.int).
  - **ATC and LOINC** (checked 2026-11-26): the WHO Collaborating Centre's [terms](https://atcddd.fhi.no/copyright_disclaimer/) allow non-commercial use with a reference to the Centre, and no changes to the material. LOINC is free to use and redistribute with its notice ([Getting LOINC](https://loinc.org/?p=7451)); the licence page itself could not be read automatically. Bare codes only are committed until the owner has read both.
- **Fake data still gets real protection.** Faker's names and addresses can match real people by chance, and the point of the project is to behave as a hospital would. So identifiers are treated as personal data throughout, and every identifier the project invents (medical record number, national-ID-like number) uses a format that cannot belong to a real person, e.g. the prefix `SYN-`. Faker's built-in national ID generators, which make numbers with valid check digits, are not used.
- **Where each kind of data may go:**

  | | Repository | Hosted database | Public app | AI chat |
  | --- | --- | --- | --- | --- |
  | Generator code and rules | yes | n/a | n/a | yes |
  | A small sample (≤ 50 patients) for tests | yes | ~~yes~~ no | no | yes |
  | The full generated dataset | no (regenerated from the seed) | ~~yes~~ no | no | yes |
  | Identifiable layer (names, addresses, MRNs) | no | ~~yes, identity schema only~~ no | no | yes |
  | Pseudonymized marts | no | ~~yes~~ no | no | yes |
  | Aggregates after small-cell suppression | in docs and screenshots | yes, `marts_public` only | yes | yes |

  The data is fake, so "yes" everywhere would be legal. The table is stricter on purpose: it is the table a real hospital would need, and the tests enforce the "no" cells that matter (the public app reads only suppressed aggregates, and the hosted database holds nothing else). Everything except `marts_public` stays in the local and CI databases. (See [Changes to the spec](#changes-to-the-spec).)

## Scope

### In

1. **Generator** (`generator/`): a Python package that, from a seed and a config file, writes a complete dataset: patients, addresses, visits, diagnoses (problem list and per-visit), medication orders, lab orders and results, departments and clinicians. The same seed, config and locked dependencies (`uv.lock`) produce byte-identical output.
2. **Clinical rules** that make the data plausible: conditions drive medicines, medicines and conditions drive lab values, visits follow condition burden, nobody has a visit after death. The rule set is in [Clinical content](#clinical-content).
3. **Source schema `ehr`**: normalized (3NF), with primary and foreign keys and check constraints, the way an EHR records care.
4. **Analytical marts**: a star schema built from `ehr`, pseudonymized, for cohort and interaction questions.
5. ~~**A rule-based risk score**, computed in SQL and documented as a published or written rule, not as a model *(depends on D4)*.~~ **A prediction model with a rule baseline** (`ml/`): the chance of hyperkalaemia after starting a drug that raises potassium, from logistic regression, compared with a simple rule score. See [Prediction model](#prediction-model). (See [Changes to the spec](#changes-to-the-spec).)
6. **An app** (Streamlit): cohort builder, patient visit timeline, drug–lab interaction view, ~~risk score distribution~~ the rule score's and the model's performance, as aggregates. It runs in two modes (see [Architecture](#architecture)): **hosted**, public, aggregates only; and **local**, with the role switcher and the patient timeline.
7. **Governance pack** (`governance/`): data dictionary, pseudonymization approach, access control design, DPIA-style checklist, Art. 25 mapping, threat model.
8. **SDLC evidence**: ADRs, issues and pull requests, CI, tagged releases, a changelog.

### Out (say so in the README)

- ~~Machine learning or prediction. The risk score is a transparent rule and is called a rule.~~ Moved into scope as one model (see [Changes to the spec](#changes-to-the-spec)). Still out: any other model, deep learning, and any claim that the model works on real patients.
- Generating synthetic data *from* real data (GANs, Synthea-style models fitted to real records). This project's data comes from rules only, which is why it carries no re-identification risk.
- Free-text clinical notes, imaging, vital signs, microbiology, billing.
- Interoperability standards beyond codes: no FHIR server, no HL7 v2, no OMOP mapping. The README names them and says why they are out (scope).
- Real authentication with passwords or single sign-on. The app's roles are demonstrated with a role switcher over database roles, in local mode only.
- Clinical validity. The data is plausible, not accurate; nothing here is clinical advice. The rule score and the model must say so on screen.

## Clinical content

Decided 2026-11-26 (**D2**): all six conditions and all five interactions below ([ADR 0002](adr/0002-clinical-scope.md)). Prevalence rates and lab-value distributions are numbers in the config, checked against sources before they are written there (weeks 1–2).

| Condition (ICD-10) | Medicines (ATC) | Labs it moves (LOINC) | Rule examples |
| --- | --- | --- | --- |
| Type 2 diabetes (E11) | metformin, insulin | HbA1c, glucose | HbA1c drawn from a higher distribution; falls after metformin starts |
| Hypertension (I10) | ACE inhibitor, ARB, thiazide | potassium, creatinine | ACE inhibitor raises potassium slightly; thiazide lowers it |
| Chronic kidney disease (N18) | — | creatinine, eGFR, potassium | eGFR falls over years; stage follows eGFR |
| Heart failure (I50) | loop diuretic, spironolactone, beta blocker | sodium, potassium, NT-proBNP | Loop diuretic lowers potassium; spironolactone raises it |
| Atrial fibrillation (I48) | warfarin or a DOAC | INR | INR in range most of the time on warfarin, with excursions |
| Hyperlipidaemia (E78) | statin | LDL, ALT | LDL falls after statin starts; rare ALT rise |

Conditions co-occur at configured rates (e.g. diabetes with hypertension and CKD), and prevalence rises with age.

**Population** (decided 2026-11-26): adult hospital patients, skewed towards older ages, not the general population. Everyone is 18 or older and alive on 2016-01-01, and is followed until death or 2025-12-31 (a closed cohort; nobody joins later). The age and sex mix, the prevalence by age, the co-occurrence, the visits per year and the mortality are numbers in the config, each with a source to verify, approved by the owner before they are written there.

**Drug–lab interactions the app shows** (each one a rule the generator plants at a configured rate, and a query that finds it):

1. Hyperkalaemia (K⁺ ≥ 5.5 mmol/L) within 30 days of starting or combining an ACE inhibitor/ARB with spironolactone.
2. Hypokalaemia (K⁺ < 3.5) on a loop or thiazide diuretic.
3. INR > 4 on warfarin.
4. Metformin continued while eGFR < 30.
5. ALT > 3× upper limit after a statin starts.

Planting the effects at known rates gives the analytics a correct answer to check against: the query must find what the generator put in.

Interaction 1 is planted as a formula, not a single rate, so the model has something to learn: the chance of hyperkalaemia after a start rises with lower eGFR, higher baseline potassium, diabetes, older age and the ACE inhibitor/ARB + spironolactone combination, and falls with a loop or thiazide diuretic. Each effect's strength (a log-odds coefficient) is written in the config, so the true answer is known.

Follow-up testing is planted too: after a RAAS-inhibitor start, potassium is measured within 30 days at a configured rate, below 100%, because guidelines recommend the check but it does not always happen. The unmeasured starts are what the prediction model leaves out and counts.

## Prediction model

Decided 2026-11-26 (D4). It is included to learn the machine-learning workflow for future projects. It is a statistical model, and the project calls it one.

**The question.** A patient starts a RAAS inhibitor: an ACE inhibitor, an ARB or spironolactone (drugs acting on the renin–angiotensin–aldosterone system, all of which can raise potassium). What is the chance of hyperkalaemia (K⁺ ≥ 5.5 mmol/L) within 30 days?

| Part | Definition |
| --- | --- |
| One row per… | start of a RAAS inhibitor: the index date. A start is an order with no order of the same class in the 180 days before (a "new user" definition; decided with D2) |
| Features | Known before the index date only: age, sex, the most recent eGFR and potassium in the 365 days before (with a "missing" flag), diabetes, heart failure, CKD, the combination on the index date, a loop or thiazide diuretic on the index date |
| Outcome | Any potassium ≥ 5.5 mmol/L on days 1–30 after the index date. Starts with no potassium measured in that window are left out, and counted in the results (decided with D2). Not measured is not the same as normal |
| Baseline | A rule score, one point each for eGFR < 45, baseline K⁺ > 5.0, the combination, diabetes, age ≥ 75. Labelled as invented for this project |
| Model | Logistic regression (scikit-learn), standardized features. Its coefficients can be read and explained |

**Steps, each with its proof:**

1. **Build the cohort** from the pseudonymized marts, as the `researcher` role. Test: every feature's date is before the index date (the leakage test). Shown to fail by adding a feature taken after the index date.
2. **Split by patient**, 70/30, with a seed. A patient with several starts stays on one side. Test: no pseudonym appears in both sets.
3. **Score the baseline** on the test set.
4. **Fit the model** on the training set only. Test: the same seed gives the same coefficients.
5. **Evaluate on the test set only:** AUROC (how well it ranks patients by risk), a calibration plot (whether a predicted 20% happens about 20% of the time) and the Brier score, for the model and the baseline, with the number of starts and events.
6. **Check against the truth:** each planted effect's sign is right, and its fitted odds ratio is within a stated tolerance of the planted one.

**Enough data.** About 10 events per feature is a common minimum, so the training set needs at least 100 events. A rough estimate, with assumed rates to be checked against sources in weeks 1–2: about 35% of patients have hypertension or heart failure, about 30% of those have a new start in the window, about 70% of starts get a potassium test within 30 days, and about 8% of those show hyperkalaemia. That gives about 30 events per 5,000 patients, so the default population is **25,000** (about 150 events, about 100 in training). Index dates run from 2017-01-01, so every start has at least 365 days of history before it. Check the real count after the first generation, and raise the population if it falls short.

**Honest limits, said in the README and the model card.** The data comes from this project's own rules, so the model learns the generator, not medicine. Its scores say nothing about real patients. That is also why step 6 is possible: on real data the true effects are unknown.

**Privacy.** Predictions are per patient, so they stay in the pseudonymized marts that only `researcher` reads. The public app shows performance as aggregates only, after small-cell suppression.

## Architecture

Top to bottom, with each trust boundary:

1. **Generator** (laptop or CI): config + seed → CSV files in `data/` (gitignored), with a SHA-256 manifest.
2. **Loader** → `ehr` schema. Identifiers (name, date of birth, address, MRN) live in `ehr_identity`, separate from the clinical tables, which hold only an internal patient ID. *Boundary 1: only the steward and the clinician roles can read `ehr_identity`.*
3. **Transform** (dbt) `ehr` → `marts`: the internal ID is replaced by a keyed pseudonym; dates of birth become age bands; addresses become a region. *Boundary 2: researchers read `marts` only.*

   dbt drops and recreates its tables on every build, which removes anything attached to them. So every row-level security policy, grant and trigger on a dbt-built table is created by dbt itself, in a `post_hook` that runs in the same step as the table. A protection added afterwards by a separate script would vanish on the next build, and the table would be open until someone noticed (it would "fail open"). Roles, and functions that belong to no table, are created by a script that runs before dbt.
4. **Public layer** `marts_public`: aggregates only, cells under k suppressed. *Boundary 3: the public app's role reads only this.*
   **Publish:** a script copies the `marts_public` tables, and nothing else, from the local database to the hosted database. The hosted database never receives identifiers, pseudonyms or per-patient rows, so there is nothing more there to leak. *Boundary 5: the only data that leaves the local machine is suppressed aggregates.*
5. **App** reads with the role of the person using it, in one of two modes:
   - **Hosted** (Streamlit Community Cloud, public): reads the hosted database, which holds only `marts_public`; its secrets hold only the `public_app` database login, so it can read only `marts_public`. It shows cohort counts, interaction rates and model performance, all suppressed below k. No role switcher, no patient timeline. A bug cannot show more, because the hosted app has no credentials that could read more. *Boundary 4: the internet sees only what `public_app` can read.*
   - **Local** (anyone's own machine, from the five-command setup): the role switcher over the `clinician_<dept>`, `researcher`, `data_steward` and `public_app` logins, the patient timeline and the identifiable screens. Shown in the README with screenshots and a short recording.

## Questions it answers

1. How many patients have each condition and combination, by age band and sex? (Cohort sizes, and whether the generator's prevalence is what the config asked for.)
2. What does one patient's history look like on a timeline: visits, diagnoses, drugs, labs?
3. For each drug–lab rule above: how many exposures, how many events, at what rate, and how soon after the drug started?
4. Which patients are on two interacting drugs at once, and what happened to their potassium?
5. ~~How is the risk score distributed, and how does it differ by condition?~~ How well do the rule score and the model predict hyperkalaemia after a RAAS-inhibitor start, and does the model beat the rule?
6. How does HbA1c change in the year after metformin starts?
7. Data quality: orphan rows, values outside physiological limits, visits after death. Expected to be zero, and tested.
8. Does the model recover the effects the generator planted, and how close are its odds ratios to the planted ones?

Before building the marts, outline each question's SQL against them, and look for anything the model is missing.

## Security and compliance deliverables

Built as if the data were real patients' data. Say that sentence in the README.

| Deliverable | What it contains | Proof it works |
| --- | --- | --- |
| `governance/data-dictionary.md` | Every table and column: meaning, type, allowed values, personal-data class (direct identifier, quasi-identifier, health data, none), and which roles can read it | A test fails if any column in the database is missing from the dictionary, or vice versa |
| `governance/pseudonymization.md` + code | Keyed pseudonym (HMAC-SHA-256) with the key outside the database; why a plain hash is not enough; key rotation; who can re-link and how | Same input and key → same pseudonym; new key → every pseudonym changes and nothing else; no identifier from `ehr_identity` appears in any mart |

A role × object matrix | A pytest connects as each role and checks what it can and cannot read, matching the matrix cell by cell |
| Small-cell suppression | `marts_public` hides any count below k (proposed k = 10) | A test builds a cohort of fewer than k patients and checks the public layer shows it as suppressed |
| Audit | A log of who re-linked a pseudonym and when, which the steward cannot edit | A re-link adds a row; the steward's delete fails |
| Publish step | A script that copies only the `marts_public` tables to the hosted database | After publishing, a test lists every schema and table in the hosted database and fails if anything other than `marts_public` is there |
| Hosted/local split | The hosted app's secrets template lists only the `public_app` login; in hosted mode the role switcher and timeline are not built | A test runs the app in hosted mode and checks that no role switcher or timeline appears; the role test checks that `public_app` reads only `marts_public` |
| `governance/dpia.md` | A DPIA-style checklist following Art. 35(7): description and purpose, necessity and proportionality, risks to people, measures. Written for the scenario "this system holds real patient data" | Each measure in it links to the file or test that implements it |
| `governance/privacy-by-design.md` | Art. 25 mapping: each principle in Art. 5 (minimization, purpose limitation, storage limitation, integrity) → what the system does → where | Each row links to code or a test |
| `governance/threat-model.md` | STRIDE table over the trust boundaries above, and what changes with real data | Each claim checked against the running system |
| Secrets hygiene | `.env.example`, gitleaks in pre-commit and CI, the pseudonymization key never in the repository | CI fails on a planted fake key on a throwaway branch |
| `governance/model-card.md` | Intended use (learning and demonstration only, not clinical use), training data and its limits, features, metrics with counts, the planted-effect check, and the regulatory position: a model learned from data is likely an "AI system" under the EU AI Act (Art. 3(1)), unlike a rule written by hand (*to verify against the Act's text before it is written*) | Every number in it comes from the evaluation run, which writes them to a file the card links to |

## Generator proofs

| Claim | Test |
| --- | --- |
| Reproducible | Same seed, config and locked dependencies → same SHA-256 manifest; a different seed → a different manifest |
| Prevalence matches the config | Each condition's rate within a stated tolerance of its target, for a population of N |
