# Synthetic EHR + "Privacy-by-Design": project spec

> The source of truth. Written before any code. When building shows a part to be wrong, change it here and record why under [Changes to the spec](#changes-to-the-spec).

Status: **draft, 2026-11-15.** The decisions in [Open decisions](#open-decisions) are the owner's to make; each has a recommendation. Until they are made, the parts that depend on them are marked *(depends on D1)* and so on.

A realistic but entirely fake electronic health record (EHR): patients, visits, diagnoses, medications and lab results, generated in Python with `Faker` and explicit clinical rules. On top of it: a normalized source schema, analytical marts, a small app for cohorts, visit timelines and drug–lab interactions, and a governance pack that treats the fake data as if it were real.

## What this proves

The CV line: "Built a synthetic EHR generator with clinically plausible rules, a normalized and an analytical schema, and a cohort-exploration app, designed privacy-by-design: pseudonymization, role-based access, small-cell suppression, a data dictionary and a DPIA-style assessment, each with a test that runs in CI."

| Claim | Where the proof lives |
| --- | --- |
| Understands clinical data well enough to fake it convincingly | `generator/rules/` and `docs/clinical-rules.md`: each rule has its clinical reason, and a plausibility test checks it in the output |
| Can design a relational schema for two purposes | `ehr` schema (normalized, for recording care) and `marts` (star schema, for analysis), with `docs/data-model.md` stating the grain of every fact |
| Can build an application, not only queries | The hosted app: cohort filters, visit timeline, drug–lab view |
| Builds privacy in from the start (GDPR Art. 25), and can prove it | `governance/`: pseudonymization, access control, suppression, each with a test that is shown to fail when the control is removed |
| Follows a software development life cycle on purpose | Spec → ADRs → issues → pull requests → CI → tagged releases with a changelog, all visible in the repository |
| Can write the documents a privacy officer asks for | `governance/data-dictionary.md`, `governance/dpia.md`, `governance/access-control.md`, `governance/pseudonymization.md` |

## Data

- **Source and licence:** none. Every row is generated by this project's code from a seed. No real person's data is used at any stage, and the generator never reads real records, so no real person can be re-identified from it.
- **Codes used inside the data:** ICD-10 for diagnoses, ATC for medicines, LOINC for lab tests, a few dozen codes each. Their terms of use must be checked and written in the README before they are committed (checklist step 2). *To verify; not checked yet.*
- **Fake data still gets real protection.** Faker's names and addresses can match real people by chance, and the point of the project is to behave as a hospital would. So identifiers are treated as personal data throughout, and every identifier the project invents (medical record number, national-ID-like number) uses a format that cannot belong to a real person, e.g. the prefix `SYN-`. Faker's built-in national ID generators, which make numbers with valid check digits, are not used.
- **Where each kind of data may go:**

  | | Repository | Hosted database | Public app | AI chat |
  | --- | --- | --- | --- | --- |
  | Generator code and rules | yes | n/a | n/a | yes |
  | A small sample (≤ 50 patients) for tests | yes | yes | no | yes |
  | The full generated dataset | no (regenerated from the seed) | yes | no | yes |
  | Identifiable layer (names, addresses, MRNs) | no | yes, identity schema only | no | yes |
  | Pseudonymized marts | no | yes | no | yes |
  | Aggregates after small-cell suppression | in docs and screenshots | yes | yes | yes |

  The data is fake, so "yes" everywhere would be legal. The table is stricter on purpose: it is the table a real hospital would need, and the tests enforce the "no" cells that matter (the public app reads only suppressed aggregates).

## Scope

### In

1. **Generator** (`generator/`): a Python package that, from a seed and a config file, writes a complete dataset: patients, addresses, visits, diagnoses (problem list and per-visit), medication orders, lab orders and results, departments and clinicians. The same seed and config produce byte-identical output.
2. **Clinical rules** that make the data plausible: conditions drive medicines, medicines and conditions drive lab values, visits follow condition burden, nobody has a visit after death. The rule set is in [Clinical content](#clinical-content).
3. **Source schema `ehr`**: normalized (3NF), with primary and foreign keys and check constraints, the way an EHR records care.
4. **Analytical marts**: a star schema built from `ehr`, pseudonymized, for cohort and interaction questions.
5. **A rule-based risk score**, computed in SQL and documented as a published or written rule, not as a model *(depends on D4)*.
6. **An app** *(depends on D3)*: cohort builder, patient visit timeline, drug–lab interaction view, risk score distribution.
7. **Governance pack** (`governance/`): data dictionary, pseudonymization approach, access control design, DPIA-style checklist, Art. 25 mapping, threat model.
8. **SDLC evidence**: ADRs, issues and pull requests, CI, tagged releases, a changelog.

### Out (say so in the README)

- Machine learning or prediction. The risk score is a transparent rule and is called a rule.
- Generating synthetic data *from* real data (GANs, Synthea-style models fitted to real records). This project's data comes from rules only, which is why it carries no re-identification risk.
- Free-text clinical notes, imaging, vital signs, microbiology, billing.
- Interoperability standards beyond codes: no FHIR server, no HL7 v2, no OMOP mapping. The README names them and says why they are out (scope).
- Real authentication with passwords or single sign-on. The app's roles are demonstrated with a role switcher over database roles *(depends on D3)*.
- Clinical validity. The data is plausible, not accurate; nothing here is clinical advice. The risk score must say so on screen.

## Clinical content

The proposal below is the recommendation for **D2**; the owner chooses and adjusts it. Numbers are starting points to be checked against sources before they are written into the config.

| Condition (ICD-10) | Medicines (ATC) | Labs it moves (LOINC) | Rule examples |
| --- | --- | --- | --- |
| Type 2 diabetes (E11) | metformin, insulin | HbA1c, glucose | HbA1c drawn from a higher distribution; falls after metformin starts |
| Hypertension (I10) | ACE inhibitor, ARB, thiazide | potassium, creatinine | ACE inhibitor raises potassium slightly; thiazide lowers it |
| Chronic kidney disease (N18) | — | creatinine, eGFR, potassium | eGFR falls over years; stage follows eGFR |
| Heart failure (I50) | loop diuretic, spironolactone, beta blocker | sodium, potassium, NT-proBNP | Loop diuretic lowers potassium; spironolactone raises it |
| Atrial fibrillation (I48) | warfarin or a DOAC | INR | INR in range most of the time on warfarin, with excursions |
| Hyperlipidaemia (E78) | statin | LDL, ALT | LDL falls after statin starts; rare ALT rise |

Conditions co-occur at configured rates (e.g. diabetes with hypertension and CKD), and prevalence rises with age.

**Drug–lab interactions the app shows** (each one a rule the generator plants at a configured rate, and a query that finds it):

1. Hyperkalaemia (K⁺ ≥ 5.5 mmol/L) within 30 days of starting or combining an ACE inhibitor/ARB with spironolactone.
2. Hypokalaemia (K⁺ < 3.5) on a loop or thiazide diuretic.
3. INR > 4 on warfarin.
4. Metformin continued while eGFR < 30.
5. ALT > 3× upper limit after a statin starts.

Planting the effects at known rates gives the analytics a correct answer to check against: the query must find what the generator put in.

## Architecture

Top to bottom, with each trust boundary:

1. **Generator** (laptop or CI): config + seed → CSV files in `data/` (gitignored), with a SHA-256 manifest.
2. **Loader** → `ehr` schema. Identifiers (name, date of birth, address, MRN) live in `ehr_identity`, separate from the clinical tables, which hold only an internal patient ID. *Boundary 1: only the steward and the clinician roles can read `ehr_identity`.*
3. **Transform** *(depends on D1)* `ehr` → `marts`: the internal ID is replaced by a keyed pseudonym; dates of birth become age bands; addresses become a region. *Boundary 2: researchers read `marts` only.*
4. **Public layer** `marts_public`: aggregates only, cells under k suppressed. *Boundary 3: the public app's role reads only this.*
5. **App** reads with the role of the person using it.

## Data model

### Source schema `ehr` (normalized)

| Table | One row per… | Notes |
| --- | --- | --- |
| `ehr_identity.patient_identity` | patient | Name, date of birth, sex, MRN (`SYN-…`), address. The only place identifiers live |
| `patient` | patient | Internal ID, sex, birth year, date of death |
| `department` | department | Name, specialty |
| `clinician` | clinician | Fake name, department |
| `encounter` | visit | Patient, department, clinician, type (outpatient, emergency, inpatient), start, end |
| `condition` | condition on the problem list | Patient, ICD-10 code, onset, resolved |
| `encounter_diagnosis` | diagnosis recorded at a visit | Encounter, ICD-10 code, primary flag |
| `medication_order` | prescription | Patient, encounter, ATC code, dose, start, stop |
| `lab_order` / `lab_result` | order / result | Encounter, LOINC code, value, unit, reference range, time |
| Code tables | code | `icd10_code`, `atc_code`, `loinc_code` |

### Marts (star schema, pseudonymized)

State the grain in one sentence before writing SQL.

| Fact | Grain: one row per… | Measures | Dimensions |
| --- | --- | --- | --- |
| `fact_encounter` | visit | length (hours), diagnosis count | patient, department, encounter type, date |
| `fact_lab_result` | lab result | value, abnormal flag | patient, lab test, date, encounter |
| `fact_medication_exposure` | continuous period a patient takes one drug | days exposed | patient, drug, start date, stop date |
| `fact_drug_lab_event` | lab result that falls inside an exposure window of a drug linked to that test | value, days since drug start, rule triggered | patient, drug, lab test, date |
| `fact_risk_score` | patient on the reference date | score, components | patient |

| Dimension | Attributes | Note |
| --- | --- | --- |
| `dim_patient` | pseudonym, sex, age band, region, condition flags | No name, MRN, exact birth date or address |
| `dim_date` | date, year, month, weekday | |
| `dim_department` | name, specialty | |
| `dim_drug` | ATC code, name, class | |
| `dim_lab_test` | LOINC code, name, unit, reference range | |
| `dim_diagnosis` | ICD-10 code, title, chapter | |

## Questions it answers

1. How many patients have each condition and combination, by age band and sex? (Cohort sizes, and whether the generator's prevalence is what the config asked for.)
2. What does one patient's history look like on a timeline: visits, diagnoses, drugs, labs?
3. For each drug–lab rule above: how many exposures, how many events, at what rate, and how soon after the drug started?
4. Which patients are on two interacting drugs at once, and what happened to their potassium?
5. How is the risk score distributed, and how does it differ by condition?
6. How does HbA1c change in the year after metformin starts?
7. Data quality: orphan rows, values outside physiological limits, visits after death. Expected to be zero, and tested.

Before building the marts, outline each question's SQL against them, and look for anything the model is missing.

## Technology stack

| Layer | Choice | Why this and not the alternative |
| --- | --- | --- |
| Language | Python 3.12, managed with uv | One tool for environments and the lock file |
| Generator | `Faker` for names and addresses; `numpy` random generator with a seed for clinical values | Faker is not built for clinical values; one seeded generator makes output reproducible |
| Config | YAML file validated with `pydantic` | Rates and rules change without code changes, and a typo fails loudly |
| Database | *(D1)* PostgreSQL 16: local in Docker, hosted on a free tier | Roles, row-level security and views are the access-control story; DuckDB has no roles |
| Transform | *(D1)* dbt-core with dbt-postgres, or plain SQL scripts | dbt gives tests and lineage; plain SQL is less to learn |
| App | *(D3)* Streamlit on Streamlit Community Cloud, or FastAPI | See D3 |
| Tests | pytest, plus dbt tests if dbt is chosen | |
| Lint and secrets | ruff, sqlfluff, gitleaks in pre-commit and CI | From the starter |
| CI | GitHub Actions, actions pinned to commit hashes | From the starter |
| Docs | Markdown, Mermaid diagrams, ADRs in MADR format | |

## Security and compliance deliverables

Built as if the data were real patients' data. Say that sentence in the README.

| Deliverable | What it contains | Proof it works |
| --- | --- | --- |
| `governance/data-dictionary.md` | Every table and column: meaning, type, allowed values, personal-data class (direct identifier, quasi-identifier, health data, none), and which roles can read it | A test fails if any column in the database is missing from the dictionary, or vice versa |
| `governance/pseudonymization.md` + code | Keyed pseudonym (HMAC-SHA-256) with the key outside the database; why a plain hash is not enough; key rotation; who can re-link and how | Same input and key → same pseudonym; new key → every pseudonym changes and nothing else; no identifier from `ehr_identity` appears in any mart |
| `governance/access-control.md` + `security/roles.sql` | Roles: `clinician_<dept>` (identifiable, own department only, row-level security), `researcher` (marts only), `data_steward` (re-linking), `public_app` (suppressed aggregates only), `etl` (writes, cannot read the audit log). A role × object matrix | A pytest connects as each role and checks what it can and cannot read, matching the matrix cell by cell |
| Small-cell suppression | `marts_public` hides any count below k (proposed k = 10) | A test builds a cohort of fewer than k patients and checks the public layer shows it as suppressed |
| Audit | A log of who re-linked a pseudonym and when, which the steward cannot edit | A re-link adds a row; the steward's delete fails |
| `governance/dpia.md` | A DPIA-style checklist following Art. 35(7): description and purpose, necessity and proportionality, risks to people, measures. Written for the scenario "this system holds real patient data" | Each measure in it links to the file or test that implements it |
| `governance/privacy-by-design.md` | Art. 25 mapping: each principle in Art. 5 (minimization, purpose limitation, storage limitation, integrity) → what the system does → where | Each row links to code or a test |
| `governance/threat-model.md` | STRIDE table over the trust boundaries above, and what changes with real data | Each claim checked against the running system |
| Secrets hygiene | `.env.example`, gitleaks in pre-commit and CI, the pseudonymization key never in the repository | CI fails on a planted fake key on a throwaway branch |

The DPIA and the GDPR texts are drafts until the owner rewrites them. They describe what the law asks and what the system does; they are not legal advice. Cite article numbers.

## Generator proofs

| Claim | Test |
| --- | --- |
| Reproducible | Same seed and config → same SHA-256 manifest |
| Prevalence matches the config | Each condition's rate within a stated tolerance of its target, for a population of N |
| Planted interactions are found | Each drug–lab rule's rate in the marts within tolerance of the configured rate |
| Clinically consistent | No visit after death or before birth; no drug before its indication's onset; lab values within physiological limits; HbA1c higher in diabetics than in others |
| No real identifiers | Every MRN matches the `SYN-` pattern; no national-ID-format numbers anywhere |

## Open decisions

The owner decides these; each has options and a recommendation.

| # | Decision | Options | Recommendation |
| --- | --- | --- | --- |
| D1 | Database and transforms | (a) Postgres + dbt; (b) Postgres + plain SQL; (c) DuckDB + dbt | **(a)**: Postgres has the roles and row-level security that the access-control design needs; dbt brings tests, docs and lineage that analytics jobs ask for |
| D2 | Clinical scope | The six conditions and five interactions above, or fewer / different ones | **The six above**: they share labs (potassium, creatinine), so the interactions arise naturally. Cut to four if time runs short |
| D3 | App | (a) Streamlit with a role switcher; (b) FastAPI with token-scoped roles + a minimal front end; (c) both | **(a)**: one deployable app, free hosting; the role switcher shows the same screen giving different answers to different roles. (b) shows more software engineering but doubles the work |
| D4 | Risk score | (a) CHA₂DS₂-VASc for the AF patients (a published rule); (b) an own "medication safety" score from eGFR, potassium, interacting drugs and age; (c) both | **(a) first**: a published rule is defensible in an interview and testable against its definition. Add (b) if time allows, clearly labelled as invented |
| D5 | Population and setting | Size (e.g. 5,000 patients default, scalable); Faker locale (e.g. `nl_NL`, `en_GB`) | **5,000 patients, a European locale**: fits a free hosted database and suits a GDPR story |
